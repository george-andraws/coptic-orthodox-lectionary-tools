# Lectionary data folder survey workflow

Use this reference when the requester asks for a read-only map/audit of the local Coptic Orthodox lectionary data package, source-vs-derived classification, build script I/O, or site coupling.

## Key durable finding

The downstream documentation `Coptic Orthodox Lectionary Reference/` folder is a published generated package, not the source repo. It may have no `.git` directory. The actual builder/toolchain can live separately at:

```text
$REPO_ROOT
```

That builder repo has been observed with remote:

```text
https://github.com/george-andraws/coptic-orthodox-lectionary-tools.git
```

Do not assume a machine-specific path exists in another environment. If a supplied path fails, locate the repository checkout or ask for its path before declaring data missing.

## Survey sequence

For read-only data-folder mapping tasks:

1. Resolve paths first.
   - Check requested `DATA_ROOT` exactly.
   - If a machine-specific path is stale, locate the active repository checkout.
   - Check requested site repo exactly and live equivalent, but do not fabricate site findings if the repo is absent.
2. Version-control reality:
   - Run `git rev-parse --show-toplevel` from the data root.
   - Search upward and downward for `.git`.
   - Report whether the data package is under Git.
   - Separately inspect the builder repo if found.
3. Inventory:
   - Tree two to three levels deep.
   - For each file: relative path, size, extension.
   - Exclude only obvious junk like `.DS_Store` and `__pycache__` from human tree, but note generated helper copies if relevant.
4. Data-file summaries:
   - For CSV/JSONL: row/record count, header/first record, concise purpose.
   - For JSON: keys/sample.
   - For SQLite: table list and selected table row counts/columns.
   - For PDFs/TXT: treat as source/source-extraction copies, not generated indexes.
5. Classify SOURCE vs DERIVED using build evidence, not filenames alone.
   - Source copies: `sources/*.pdf`, extracted `sources/*.txt`, `sources/KatamerosDatabase.sqlite`.
   - Derived published outputs: `data/*.csv`, `data/*.jsonl`, `BUILD_SUMMARY.json`, query helper copies under `scripts/`.
   - Curated-derived: Agpeya and special-service rows generated from hardcoded curated `ROWS` in builder scripts.
6. Script I/O:
   - Scripts physically inside the data root are usually read-only helpers (`query_lectionary.py`, `passage_normalization.py`).
   - Inspect the separate builder repo for actual builders.
   - Quote exact line numbers for path constants, reads, writes, copy/publish steps, and subprocess orchestration.
7. Dependency graph:
   - Use real filenames, not generic labels.
   - Explicitly identify the script producing `bible_chapter_lectionary_occurrences.csv/.jsonl`.
8. Site coupling:
   - If the site repo is absent, say that direct inspection is impossible.
   - You may cite existing audit notes, but label them as prior-audit evidence, not live verification.

## Core pipeline map

The observed durable pipeline is:

```text
katameros-api SQLite
  -> build_lectionary_reference.py
  -> katameros_cycle_readings.csv/.jsonl
  -> katameros_cycle_passage_index.csv/.jsonl

copticchurch.net cached/scraped daily pages
  -> build_lectionary_reference.py
  -> copticchurch_date_meta_2020_2035.csv
  -> copticchurch_date_readings_2020_2035.csv/.jsonl
  -> copticchurch_passage_index_2020_2035.csv/.jsonl
  -> source_ref_repair_report.csv/.jsonl

legacy/required Pascha and Bright Saturday artifacts
  -> build_lectionary_reference.py copy_special_datasets()
  -> pascha_day_hour_index.csv/.jsonl
  -> bright_saturday_service_order.csv/.jsonl

St_Mary_Ottawa_Katameros_Holy_Pascha_EN.txt
  -> build_pascha_source_text_index.py
  -> pascha_source_text_index.csv/.jsonl

build_special_service_reference.py curated ROWS
  -> special_service_readings_curated.csv/.jsonl
  -> special_service_passage_index.csv/.jsonl

build_agpeya_reference.py curated ROWS
  -> agpeya_hour_readings.csv/.jsonl
  -> agpeya_passage_index.csv/.jsonl

all passage indexes
  -> build_lectionary_crosswalk.py
  -> reverse_lookup_crosswalk.csv/.jsonl
  -> reverse_lookup_summary.csv

reverse_lookup_crosswalk.csv
  -> build_bible_chapter_lectionary_index.py
  -> bible_chapter_lectionary_index.csv/.jsonl
  -> bible_chapter_lectionary_occurrences.csv/.jsonl

out/data + out/scripts + out/sources + BUILD_SUMMARY.json
  -> build_lectionary_reference.py publish_verified_package()
  -> downstream documentation Coptic Orthodox Lectionary Reference package
```

## Unified CSV origin

`data/bible_chapter_lectionary_occurrences.csv` and `.jsonl` are generated by:

```text
$REPO_ROOT/build_bible_chapter_lectionary_index.py
```

They are generated from `out/data/reverse_lookup_crosswalk.csv`, then copied into the downstream documentation data package.

## Pascha source-text drift pattern

`pascha_source_text` rows originate from St. Mary Ottawa Holy Pascha extracted text:

```text
out/sources/St_Mary_Ottawa_Katameros_Holy_Pascha_EN.txt
```

and are introduced by:

```text
build_pascha_source_text_index.py
```

If the site index lacks `pascha_source_text` while the source CSV includes it, the likely cause is that the committed/generated site index was built from an older or smaller source snapshot. Confirm against the live site repo if available.

## Rebuild commands

Inside the published data folder itself there may be no rebuild command. Use the builder repo:

```bash
cd $REPO_ROOT
python3 build_lectionary_reference.py
PYTHONDONTWRITEBYTECODE=1 python3 verify_lectionary_queries.py
```

The runbook says `python3 build_lectionary_reference.py` is the standard full rebuild and runs verification as part of the build; the explicit verifier remains the post-change check.

## Output discipline for these audits

If the maintainer requests read-only mode, make exactly the requested report write and nothing else. No edits, commits, pushes, or repair attempts. If a path or repo is absent, report it plainly and distinguish live evidence from prior-audit evidence.
